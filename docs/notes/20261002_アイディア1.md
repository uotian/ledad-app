## 1. このドキュメントの読み方

本書では、会話で決まった要求を「必須要件」、詳細を具体化するための提案を「初期実装案」、選定が必要な部分を「未確定事項」として扱う。

実装時は必須要件を維持する。初期実装案は着手時のたたき台として採用できるが、変更する場合は理由を記録する。技術選定や対応形式について、本書にない決定をユーザーの合意事項として扱わない。

**PresenterとAudienceの両モードを初期リリースの対象とする。Audienceを将来機能に回さない。** 開発の順番を分けても、片方だけで初期実装が完成したとは扱わない。

## 2. コンセプト

**伝える内容と判断は本人が持ち、会議中はledadを操作して発表・質問・回答を行う。**

本人がPCを持って会議に参加し、ledadを操作する。AIが発表内容や会話を理解し、本人の代わりに音声で発表・質問・回答・進行を行う体験を目指す。

Presenterでは「資料をしっかり準備すれば、操作だけで発表と質疑応答を乗り切れる」、Audienceでは「発表を聞きながら、AIと質問を考え、操作して質問できる」を実現する。

本人が自分の言葉で話すことを必須にしない。AIが案を作り、本人が何を伝えるかを選び、AIが話す。会議の場で本人が判断し、操作すること自体が製品の中心となる体験である。

### 背景と想定利用者

- 資料は十分に作れるが、発表で緊張して苦労する人。
- 英語など、母語以外で発表・質問・回答する必要がある人。
- プレゼンテーションや会議進行の負担を減らしたい人。
- 発表や外国語が得意でも、よりスマートに会議へ参加したい人。
- 他者の発表を聞きながら、疑問を整理して質問したい人。

発表者になる機会より、参加者になる機会の方が多いという想定から、Audienceも最初から提供する。

最初の利用場面は社内説明会。将来は会社の会議全般、学会での発表などに広げる。市場規模、価格、販売方法は本書では決めない。

## 3. 利用前提と初期スコープ

### 必須要件

- 初期版は、Macへインストールして使うローカルMacアプリとする。アプリの土台はTauri 2、画面はNext.js＋React＋TypeScriptを採用する。
- アプリはMac上で動き、STT・TTS・質問／回答案の生成にはクラウドのAI APIへ接続する。AI処理まで完全にローカルで動く構成ではない。
- 本人は会議に同席し、自分のPCでledadを操作する。
- AIが別の参加者として会議サービスに入る必要はない。
- PresenterとAudienceを選んで利用できる。
- どちらのモードでも、会議の音声を聞きながら、本人がチャットでAIに指示できる。
- AIが作った質問・回答案を、本人の指示なしで会議に向けて発話しない。
- 最初は日本語を使う利用者向けに提供し、発表・発話の言語は選択可能にする。
- 会議終了後の記録を作成する。

### 初期実装の対象外

- 持ち時間に応じた原稿の短縮、発表速度や構成の自動調整。
- ベース言語を日本語以外へ切り替える機能の提供。ただし、後から追加できる設計にする。
- 本人不在でAIが会議へ参加し、独立して判断・発言する機能。

スクリプトの自動生成、会議前のリハーサル、発表音声の事前生成は追加候補とし、初期リリースの必須条件にはしない。

## 4. 本人とAIの役割

| 場面 | 本人 | AI・ledad |
| --- | --- | --- |
| 発表の準備 | 資料・原稿を用意する | 内容を取り込む |
| 発表 | 開始・停止・再開を操作する | 資料・原稿に沿って音声で話す |
| 質問への対応 | 答えるかどうかと回答内容を選ぶ | 質問を検知して複数の回答案を作る |
| 質問する準備 | 疑問や指示を入力し、質問する内容を選ぶ | 発表とチャットを踏まえて質問案を作る |
| 発言 | 話す内容を選び、発話を指示する | 選ばれた内容を音声で話す |
| 会議後 | 記録と確認事項を確認する | 議事録と質問・回答をまとめる |

チャットの送信は、AIへの私的な指示である。チャットを送信しただけで、その文章を参加者へ読み上げたり、共有画面に表示したりしない。

## 5. Presenterモード

### 5.1 会議前の準備

1. Presenterを選ぶ。
2. プレゼンテーション資料を登録する。
3. 回答の参考になる関連資料を登録する。
4. 発表スクリプトを登録する。
5. 資料の機密度と、この会議で利用できる資料を設定する。
6. 発表言語と音声入出力を設定する。
7. 本人用画面と共有画面を開き、発表できる状態にする。

スクリプトとスライドの対応づけは実装時に具体化する。初期実装案はスライド単位の原稿を確認・編集できる方式とし、登録した原稿を黙って別の内容へ変更しない。

### 5.2 発表

- 本人が「開始」を操作すると、AIが音声で発表する。
- 共有画面にスライドと字幕を表示する。
- 本人用画面には原稿、現在の位置、操作ボタン、会話、回答案、チャットを表示する。
- 本人はいつでもAIの発話を停止できる。
- 発表位置を保持し、再開できる。

### 5.3 質疑応答

1. AIが参加者の質問を音声から検知する。
2. 本人用画面に質問と、必要に応じてその訳を表示する。
3. 利用可能な資料と会話の文脈から複数の回答案を作る。生成中は「考え中…」を点滅表示する。
4. 本人が回答するかどうかを判断する。
5. 本人が回答案を選び、発話を指示する。
6. AIが選ばれた案を音声で話す。
7. 発表途中であれば、本人の操作で発表へ戻る。

本人は質問を聞きながら「短く答えて」「この事例を使って」「その点は未確定として答えて」などをチャット入力できる。AIは指示を反映した回答案を提示する。

質問を検知しただけで回答を発話しない。検知時に発表を自動停止するかは未確定。初期実装案では発表を続けながら質問を通知し、本人が停止または回答の実行を選ぶ。回答へ切り替える際は、発表音声と回答音声を重ねず、中断位置を保持する。

## 6. Audienceモード

### 6.1 利用開始

1. Audienceを選ぶ。
2. 聞き取る音声の入力元と、質問に使う発話言語を設定する。
3. 「開始」を操作し、発表を聞く。

Audienceは、他者の発表資料を入手できない場合でも、聞き取った内容から利用できる設計にする。これは初期実装案であり、資料のアップロードを開始の必須条件にしない。相手がledadを使っていることも前提にしない。

### 6.2 質問を作る・質問する

1. AIが発表内容を聞き取り、会話の文脈を保持する。
2. AIに質問案を考えさせる。本人は必要に応じてチャットで観点や疑問を入力する。
3. AIが、聞いた内容とチャットに基づく質問案を本人向けに提示する。
4. 本人が質問するかどうかを判断し、案を選ぶ・調整する。
5. 本人が発話を指示すると、AIが選ばれた質問を音声で話す。
6. 相手の回答を聞き取り、その後の質問や会議記録に利用する。

チャット入力例：

- 「導入費用について質問を考えて」
- 「今の説明の前提を確認したい」
- 「その質問をもう少し簡潔にして」

質問案を自動で継続生成するか、本人の操作で生成するかは未確定。初期実装案は「質問案を作る」操作またはチャット送信をきっかけに生成する方式。候補を生成しても、自動で会議に向けて発話しない。

Audienceが質問した後も聞き取りとチャットを継続できるようにする。Presenterと同じ候補操作・音声出力・記録の仕組みを使う。

## 7. 共通の画面・操作仕様

### 7.1 画面構成

| 画面 | 内容 |
| --- | --- |
| セッション準備 | モード、言語、音声入出力、資料の登録・機密度 |
| Presenter操作画面 | 原稿と発表位置、質問と訳、回答案、チャット、AIの状態、操作ボタン |
| Presenter共有画面 | スライド、AIの発話字幕。回答案・補足資料・私的チャットは表示しない |
| Audience操作画面 | 聞き取った発表内容と訳、質問案、チャット、AIの状態、操作ボタン |
| 会議後の記録 | 議事録、質問・回答、未回答事項、対応事項 |

「Audienceモード」と「Presenterの共有画面」は別のもの。Audienceモードは参加者本人が質問を作るために操作する機能である。

PresenterはPowerPointの発表者ツールに近い体験を想定する。本人用と共有用のウィンドウを分け、外部ディスプレイまたは会議サービスには共有用のみを表示する方式を初期実装案とする。

### 7.2 候補の操作

質問案・回答案には、本人が短時間で選べる表示と操作を用意する。

初期実装案：

- 候補は2〜3案を目安とし、短い見出しと内容を表示する。候補を無理に増やさない。
- 回答の事実関係は共通にし、長さ・観点・詳しさの違いを示す。
- ベース言語で確認でき、実際に話す言語の文章も確認できる。
- 候補の選択と「話す」操作を分ける。選択だけでは発話しない。
- チャットで修正・再生成できる。
- 回答・質問を保留または見送る操作を用意する。
- 指示を反映して候補が更新されたら、更新後の内容を確認して発話する。古い候補の選択状態を自動的に引き継がない。

「話す」を押した後に、別の候補や別の内容へ勝手に差し替えない。実際の発話対象を固定する。

### 7.3 開始・停止・再開・終了

操作名は必須。細部について、次を初期実装案とする。

| 操作 | Presenter | Audience |
| --- | --- | --- |
| 開始 | 聞き取りを開始し、準備した原稿の発表を始める | 発表の聞き取りを開始する |
| 停止 | AIの発話・発表進行を止め、位置を保持する | 質問の発話中なら止める |
| 再開 | 保持した発表位置から再開する | 中断した質問があれば、本人の指示で再開する |
| 終了 | 入出力を終了し、記録作成へ進む | 入出力を終了し、記録作成へ進む |

初期実装案では「停止」はAIの発話の停止とし、聞き取りは続ける。聞き取りを止める操作は別に設け、現在聞いているかが画面で分かるようにする。停止できる発話がなければ「停止」を、中断している発話や発表がなければ「再開」を無効にする。

発話停止後に残っていた音声が再生されたり、終了後に遅れて届いた生成結果が自動で話し始めたりしないこと。

### 7.4 状態表示

少なくとも「聞き取り中」「考え中…」「選択待ち」「発話中」「発話停止中」「終了」「エラー」を区別する。聞き取りと生成など、同時に進む処理は別の状態として表示する。

「考え中…」は生成中のみ点滅し、完了・取消・失敗で止める。初期実装案では本人用画面に表示する。共有画面への表示有無は今後決める。

音声の許可がない、通信に失敗した、資料を読み取れない場合は、処理が完了したように見せず、理由と再試行方法を表示する。

## 8. 言語仕様

| 設定 | 意味 | 初期提供 |
| --- | --- | --- |
| ベース言語 | アプリ表示、質問・回答案の確認など、本人が使う言語 | 日本語 |
| 発表・発話言語 | AIが会議へ向けて話す言語 | 日本語・英語・中国語などを想定。対応範囲は選定時に確定 |

Presenterの説明だけでなく、回答とAudienceの質問にも発話言語の設定を適用する。

例：日本語で英語の質問内容と回答案を確認し、選んだ回答をAIが英語で話す。Audienceでは、日本語で質問を指示し、AIが英語の質問を作って話す。

第2段階ではベース言語も選べるようにする。英語を使う人が、英語で操作・確認しながら日本語で発表する場合にも対応できる設計にする。

初期実装案では質疑応答も設定した発話言語を使用する。質問者の言語に合わせた自動切り替え、資料自体の翻訳、原文と訳文の併記方法、中国語の音声・文字種の対応範囲は未確定。

## 9. 資料・機密度・生成内容

### 必須要件

- Presenterの資料は、発表用資料・関連資料・スクリプトとして区別して登録できる。
- 資料に機密度ラベルを付けられる。
- 回答案は関連資料と会話の文脈を踏まえて作る。
- 共有画面には、回答案や私的な補足資料を出さない。

### 初期実装案

- 機密度の名称は「公開」「社内限定」「関係者限定」「本人のみ」を仮案とする。
- 資料単位でラベルを設定し、会議ごとに利用できる資料を指定する。
- 表示してよい資料と、音声回答の根拠として使ってよい資料の両方を制御する。
- 利用を許可していない資料は、会議向けの質問・回答を作る際の参照対象から外す。
- 根拠となる資料名やページを本人が確認できるようにする。
- 資料に根拠がない場合は、推測を確定事項にせず、「確認して後ほど回答する」などを候補として提示する。

ラベルの最終的な定義、未設定資料の扱い、ページ単位の機密度、チャットで追加した情報の扱いは未確定。名称を画面に表示するだけで、利用制御まで実装したと扱わない。

## 10. 会議後の成果物と記録

両モードで、聞き取れた会話と実際の発話に基づく議事録・質問一覧を作る。

- 発表・会話の要点。
- 質問と、実際に話された回答。
- 未回答・要確認の質問。
- 確認できた決定事項と次のアクション。

Audienceでは、自分が質問した内容と相手の回答も対象にする。選ばなかった候補や私的なチャットを、会議での発言として混ぜない。聞き取れなかった内容を補って実際の発言として記録しない。

途中で止めた音声は、用意した全文を話し終えた扱いにしない。発話の完了・中断を区別する。

初期実装案は、アプリ内での確認とMarkdown出力。保存先・保存期間・音声自体の保存有無・削除方法は、実装時に選定して明示する。

### 実装上区別して管理する情報

| 情報 | 保持する内容の例 |
| --- | --- |
| 会議セッション | モード、言語、入力元、状態、開始・終了時刻 |
| 資料 | 種類、機密度、会議での利用可否、ページ情報 |
| 聞き取った発言 | 原文、訳、時刻、認識の確定状態 |
| 質問・回答案 | 対象の質問、本文、発話用本文、根拠、修正履歴、選択状態 |
| 実際の発話 | 対象の候補・原稿、開始・停止・完了、発表の再開位置 |
| 私的なチャット | 指示内容、対象の質問・候補、反映状態 |

これは設計上の整理であり、データベース製品や具体的なスキーマの指定ではない。

## 11. 技術方針と品質目標

STT（音声から文字への変換）、資料・会話に基づくAIの生成、TTS（文字から音声への変換）を組み合わせる。**アプリはTauri 2のローカルMacアプリ、画面はNext.js＋React＋TypeScript、STT・TTSはGemini系のAPI、質問・回答案の生成はOpenAIのResponses APIとする。** 具体的なモデルと音声処理の実装は着手時に選定する。将来はOpenAIのエージェント機能を利用して、資料の検索や複数段階の処理を拡張することを検討する。

技術を選ぶ際は、PresenterとAudienceの両方で、音声を聞きながらチャット入力でき、本人の指示で音声を出せることを基準にする。自分のTTS出力を新しい質問と誤認し続けないよう、実機で音声の回り込みも確認する。

次の3点は、製品として作り込む設計目標である。

| 目標 | 実装時に確認すること |
| --- | --- |
| 会話として使える応答速度 | 聞き取り、候補生成、本人の選択、TTS開始までの時間を区別して計測する |
| 話すより負担の少ない操作 | 候補の違いがすぐ分かり、会議を聞きながら少ない操作で発話できる |
| 分かりやすい発表と対話 | 原稿の構成、話し方、字幕・資料との同期、質問への応答を確認する |

具体的な秒数や性能基準は、実際の音声サービスを使った試作で決める。画面のモックや固定応答だけで、音声を含む一連の動作が完成したとは扱わない。

| ID | 確認シナリオ | 期待する結果 |
| --- | --- | --- |
| AC-01 | アプリを起動しモードを選ぶ | PresenterとAudienceの両方へ進める |
| AC-02 | Audienceで資料なしに会議を聞く | 内容を取り込み、チャット入力と質問案の作成ができる |
| AC-03 | Audienceで質問案を選ぶ | 選択だけでは話さず、本人の発話操作で選んだ内容を話す |
| AC-04 | Presenterで資料・原稿を登録して開始する | AIが原稿に沿って音声で発表し、共有画面に資料と字幕を表示する |
| AC-05 | Presenterの発表中に質問する | 質問を検知して複数の回答案を提示し、本人の指示で回答する |
| AC-06 | 回答後に発表を再開する | 保持した発表位置から続けられる |
| AC-07 | 両モードで聞きながらチャット指示する | 聞き取りを継続しつつ指示を反映した候補を作り、指示自体は会議へ公開しない |
| AC-08 | 発話を停止・再開・終了する | 音声が停止し、意図した内容を再開できる。終了後に残った音声を再生しない |
| AC-09 | 日本語で操作し外国語を発話言語にする | 本人が日本語で確認した内容を、選定した対応言語で話せる |
| AC-10 | 候補生成を開始し、完了・失敗させる | 「考え中…」が適切に点滅・終了し、選択待ちとエラーを区別できる |
| AC-11 | Presenterの共有画面を開く | 原稿、未選択候補、私的チャット、非共有資料が表示されない |
| AC-12 | 会議で利用できない資料を登録する | 対象資料が共有表示や会議向け生成の参照元にならない |
| AC-13 | 会議を終了し記録を見る | 両モードで記録を作れ、実際の発言と未発話の候補・私的指示が混ざらない |
| AC-14 | マイク拒否や生成サービスの失敗を起こす | 理由と再試行方法が分かり、勝手に発話しない |
| AC-15 | Tauri版を本番ビルドし、開発サーバーを止めて起動する | 組み込んだNext.jsの画面で両モードを使える。AI通信は選定したネイティブ処理または外部サーバーを通り、開発用のNext.js APIルートに依存しない |

## 14. 技術構成の提案（2026年10月2日時点）

Tauri 2のローカルMacアプリとして、画面はNext.js＋React＋TypeScript、STT・TTSはGemini系API、質問・回答案の生成はOpenAI Responses APIを使う方針とする。以下の具体的なモデルと音声・保存処理の構成は候補であり、利用可能なアカウントと実機での検証はまだ行っていない。実装時に利用可否と最新仕様を確認する。

### 音声・生成の構成

| 役割 | 提案する候補 | ledadでの用途 |
| --- | --- | --- |
| STT | Gemini Live Transcription：`gemini-3.5-transcribe-live` | 会議音声を継続的に聞き取り、途中の文字起こしと確定した文字起こしを扱う |
| 質問・回答案の生成 | OpenAI Responses API＋Structured Outputs（具体的なモデルは未選定） | 本人向け本文・発話用本文・根拠などを分けた候補を作る |
| TTS | `gemini-3.8-flash-lite-tts`を第一候補にし、`gemini-3.8-flash-tts`と比較 | 本人が選んだ本文を音声にする。発話開始までの時間と発音・音質を実音声で比較する |

処理の流れは「音声の取り込み → Gemini STT → OpenAI Responses APIで文脈と利用可能な資料に基づく候補生成 → 本人の選択・発話指示 → Gemini TTS → 音声出力」とする。

Gemini Liveの音声会話エージェントと、Live Transcriptionによる文字起こしは区別する。ledadでは候補を本人が選ぶことが中心なので、聞き取り・候補生成・発話の開始をアプリ側で個別に制御する構成を提案する。

### 初期実装と将来のエージェント化

初期実装はResponses APIで質問案・回答案を生成し、会話の文脈、参照可能な資料、本人のチャット指示を入力する。Structured Outputsで画面表示用本文・発話用本文・根拠を分けて返す方式を提案する。

将来は、資料の検索、根拠の確認、候補の修正などの複数段階の処理を、OpenAIのエージェント機能で扱うことを検討する。公式に確認できた候補はAgents SDKであり、Responses APIを土台とする上位の仕組みとして利用できる。

会話で言及された「AgentAI」が指す具体的な製品・APIは未特定。将来採用する製品名は確定せず、エージェント化の方針として記録する。

エージェント化しても、会議に向けて話す内容の選択と発話指示は本人が行う。質問案・回答案を返す処理と、TTSを実行する処理を分け、生成の仕組みを拡張しても操作画面の流れを保てる設計にする。

### アプリの構成案

| 部分 | 提案 |
| --- | --- |
| Macアプリの土台 | Tauri 2（採用方針） |
| 操作画面・共有画面 | Next.js＋React＋TypeScript（採用方針） |
| macOSの音声取得 | ScreenCaptureKitなどのネイティブAPIをSwiftの補助モジュールから利用し、Tauri側と接続 |
| セッション・資料・記録の保存 | SQLiteとローカルファイル |
| 初期のスライド表示 | PDF.js。初期対応をPDFと原稿テキストから始める案。PowerPointの直接対応は別途選定 |

初期版はこのMacアプリ構成を採用する。ブラウザから利用するWebアプリの提供は初期スコープに含めない。音声・保存処理の詳細は上記の案をもとに具体化する。

### Next.jsとTauriの組み合わせ

Next.jsはApp Routerを使用する案とし、Tauri版では`output: 'export'`で画面を静的に書き出す。生成した`out`ディレクトリをTauriの`frontendDist`に指定する。

静的書き出しでも、画面上のチャット入力、字幕更新、候補の選択などはクライアント側で実行できる。TauriのAPIやブラウザ専用のAPIを呼ぶ処理は、ビルド時に実行されないよう、クライアントの実行環境で扱う。

役割を次のように分ける。

- Next.js：Presenter・Audienceの操作画面、チャット、候補表示、共有画面。
- Tauri・Rust／Swift：ウィンドウ、ファイル、音声取得・再生などのネイティブ処理。
- AIへの通信：Tauri側の処理、または別途用意する外部サーバー。通信の担当は実装時に選定する。

Tauriへ組み込む静的書き出し版では、実行時のNext.jsサーバーを前提にしない。Server Actionsや、リクエストを処理する動的なAPIルートを、AI通信・ファイル保存の実装先にしない。将来Web版を追加する場合は、サーバー機能を含む実行構成を別途設計する。

APIの認証情報を配布する画面のJavaScriptに埋め込まず、選定した通信処理側で管理する。開発環境で動くことに加え、本番ビルドで開発サーバーなしに動作することを確認する。

オンライン会議で相手の音声を取り込む経路と、ledadのTTSを会議の相手へ届ける経路は別に検証する。音声取得APIを採用しただけで、会議サービスのマイク入力へTTSを送れると扱わない。
